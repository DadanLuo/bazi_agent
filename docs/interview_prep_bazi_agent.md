## 使用说明

[返回顶部](#top)

这份手册的目标不是帮你背书，而是帮你形成“结构化表达 + 可落地细节 + 面试官追问时有展开空间”的答题方式。

建议使用顺序：

1. 先熟悉“项目介绍模板”，准备 1 分钟版和 3 分钟版口述。
2. 再重点练“全方位技术深挖题库”和“标准回答示例”。
3. 最后练“场景化面试题”，把回答组织成系统设计/排障/优化的闭环。

建议答题方法：

1. 先说背景和约束。
2. 再说为什么这样设计。
3. 然后说怎么落地。
4. 最后说结果、收益和权衡。

## 项目介绍模板

[返回顶部](#top)

### 1 分钟版本

> 我做的是一个“八字命理智能分析系统”，项目名称叫“赛博司命”。它本质上是一个基于 FastAPI + LangGraph + DashScope + ChromaDB 的 Agent 系统。用户输入出生年月日时、性别和地点后，系统会先做规则层的排盘计算和五行、格局、喜用神、流年分析，再结合 RAG 检索命理知识库，通过大模型生成结构化分析结果。  
>  
> 在工程上，我重点做了四件事：  
> 1. 把整体系统拆成 API、Agent、RAG、基础设施四层。  
> 2. 用 LangGraph 把八字分析流程编排成可观测、可回退的工作流。  
> 3. 在 RAG 层加入 chunk 级 metadata、where 过滤和 Agentic RAG 规划能力，提升召回准确性。  
> 4. 在基础设施层加入限流、超时、健康检查、降级和缓存机制，保证系统可用性。  
>  
> 这个项目的难点不只是模型接入，而是如何把规则引擎、知识检索和大模型生成整合成一条可维护、可解释、可扩展的分析链路。

### 3 分钟版本

> 这个项目是一个面向命理咨询场景的智能分析系统，名字叫“赛博司命”。业务目标是把传统八字分析从纯人工经验式解读，升级成“规则引擎 + 知识检索 + 大模型生成”的混合系统。  
>  
> 用户通过 API 提交出生信息之后，系统首先进入规则层：完成排盘、五行分析、格局判断、喜用神推导和流年分析。因为这部分是确定性逻辑，所以我优先用规则引擎和领域模型来做，避免把基础命理计算完全交给 LLM。  
>  
> 接着在 RAG 层，我把命理古籍和经验文档做成 chunk 级知识库。每个 chunk 不只是正文，还带有结构化 metadata，比如天干、地支、五行、十神、格局、主题等字段。查询时先做 metadata 抽取，构造 where 条件做精确过滤，再结合向量检索做语义召回。除此之外，我还保留了 Agentic RAG 的能力：对复杂追问先分析意图和复杂度，再决定检索策略、是否要重写 query、以及结果是否需要补检索。  
>  
> 在系统工程层面，我使用 FastAPI 暴露 API，LangGraph 负责编排工作流，中间件层负责日志、限流和超时控制，基础设施层负责 Redis 缓存、文件会话持久化、健康检查和降级。比如 Redis 不可用时，系统不会直接不可用，而是降级到内存限流或文件存储模式。  
>  
> 这个项目对我来说最大的价值，是把“规则计算”、“知识增强”和“模型生成”拆成了可演进的模块。这样既能保证命理分析的确定性基础，又能通过 RAG 和 LLM 提升解释力和交互体验。

### 面试官常见追问入口

你讲完项目介绍后，面试官通常会顺着以下方向追问：

1. 为什么要用 LangGraph，而不是普通函数编排？
2. 为什么规则引擎和 LLM 要混合，而不是全 LLM？
3. 为什么 RAG 里要加 metadata，而不是只做向量检索？
4. 为什么做 Agentic RAG，而不是直接做 GraphRAG？
5. 这个系统怎么保证性能和稳定性？

## 项目背景与业务价值

[返回顶部](#top)

### 背景

这个项目不是单纯的“命理问答机器人”，而是一个典型的“垂直领域智能系统”。

核心背景包括：

1. 传统八字分析强依赖经验，输出一致性差。
2. 大模型擅长自然语言生成，但不擅长纯规则计算。
3. 领域知识分散在古籍、教材、经验文档中，难以直接被模型稳定利用。
4. 命理咨询存在一定敏感性，需要安全约束和内容兜底。

### 目标

项目目标可以概括为三层：

1. 规则正确：基础命理计算尽可能确定、可解释。
2. 知识增强：让生成结果能参考古籍和经验知识，而不是模型凭空发挥。
3. 工程可用：系统能启动、能压测、能追踪、能降级、能排障。

### 业务价值

从面试表达上，可以把业务价值拆成这四点：

1. 提升分析一致性：同样输入得到稳定的排盘和规则判断。
2. 提升可解释性：LLM 输出背后有 RAG 检索结果支撑。
3. 提升交互体验：用户可以追问，不需要一次性说清所有背景。
4. 提升系统可维护性：规则、知识库和生成链路可以独立演进。

## 系统总体架构

[返回顶部](#top)

### 你可以这样描述总体架构

系统整体是一个“API 驱动的多层智能工作流系统”，主要由四部分组成：

1. API 层：负责 HTTP 接口、参数校验、请求编排入口。
2. Agent/Workflow 层：负责意图识别、分析流程编排、状态流转。
3. RAG 层：负责知识库构建、metadata 过滤、向量检索和 Agentic 检索增强。
4. 基础设施层：负责缓存、会话持久化、中间件、健康检查、安全治理和降级。

### 一条主链路怎么讲

你可以用下面这条链路讲：

1. 用户请求进入 FastAPI。
2. API 层做参数校验和初始状态构造。
3. LangGraph 工作流依次执行：
   输入验证 -> 排盘 -> 五行分析 -> 格局判断 -> 喜用神 -> 流年 -> 检索 -> LLM 生成 -> 报告组装 -> 安全检查。
4. 检索阶段先做 metadata 过滤，再做向量召回。
5. 最后把结构化结果和自然语言结果返回给用户。

### 关键设计原则

1. 把确定性计算和概率性生成拆开。
2. 把知识检索和业务流程编排拆开。
3. 把可用性问题前置到中间件和基础设施层。
4. 把敏感场景下的风险控制前置到安全模块。

## 四层架构评估

[返回顶部](#top)

### 你计划的四层

1. API 层
2. Agent 层
3. RAG 层
4. 基础设施层

### 这套分层总体上是合理的

它是合理的，因为它把：

1. 外部协议
2. 业务编排
3. 知识增强
4. 通用支撑能力

区分开了，符合垂直智能系统的典型工程结构。

### 每一层的职责建议

#### API 层

职责：

1. 对外暴露 HTTP 接口
2. 参数校验和响应序列化
3. 初始状态构造
4. 把请求交给下层 Agent/Workflow

不要让 API 层承担：

1. 复杂业务判断
2. 检索逻辑
3. 长期状态管理

#### Agent 层

职责：

1. 业务流程编排
2. 意图识别与分流
3. 节点状态管理
4. 调用规则层、RAG、LLM 等能力

这一层是系统的大脑，不是简单的“模型代理”。

#### RAG 层

职责：

1. 文档清洗和切分
2. metadata 提取
3. 向量化和索引构建
4. metadata 过滤 + 向量检索
5. 复杂场景下的 Agentic RAG 规划

#### 基础设施层

职责：

1. Redis / 文件存储
2. 限流、超时、日志
3. 健康检查
4. 安全模块
5. 配置管理

### 潜在问题

这四层虽然合理，但还存在几个潜在问题。

#### 问题 1：Agent 层过厚

如果所有编排、意图识别、状态管理、工具调用都堆在 Agent 层，Agent 层会越来越臃肿。

改进建议：

1. 在 Agent 层内部再拆出 Workflow 子层。
2. Agent 只负责“决定调用哪个工作流”。
3. Workflow 负责“节点编排和状态路由”。

#### 问题 2：规则引擎层没有被单独强调

你这个项目里八字计算、格局、用神、流年分析，本质上是确定性业务能力，不应该完全淹没在 Agent 层里。

改进建议：

1. 在面试表达里补一个“领域能力层”概念。
2. 即使代码上不强拆，也要口头说明“规则引擎是独立能力模块”。

#### 问题 3：安全能力是横切关注点

安全模块既作用于输入，也作用于输出，还会影响 Agent 终态，不完全适合塞进任一业务层。

改进建议：

1. 明确把安全视为 cross-cutting concern。
2. 在回答里强调：安全检查既有 API 前置校验，也有工作流末端兜底。

#### 问题 4：基础设施层内部也可能过于耦合

像缓存、会话、日志、中间件、健康检查，其实并不是一个关注点。

改进建议：

1. 面试里可以进一步细分成：
   - 平台治理能力
   - 持久化能力
   - 运行时能力

### 最佳表达建议

如果面试官问“你这四层是不是够了”，建议这样回答：

> 四层作为高层抽象是够的，能把协议、编排、检索和基础设施区分开。但从工程治理角度看，我会在 Agent 层内部再细分工作流编排职责，并把规则引擎视为一组独立的领域服务能力。也就是说，四层适合做面试中的高层框架表达，真正落地时还需要在 Agent 和基础设施内部继续细化边界。

## 核心技术栈与选型理由

[返回顶部](#top)

### 主要技术栈

1. Python
2. FastAPI
3. LangGraph
4. DashScope / 通义千问
5. ChromaDB
6. Redis
7. Pydantic
8. 自定义规则引擎

### 为什么用 FastAPI

优点：

1. 参数校验强，Pydantic 集成好
2. 异步支持自然
3. 文档自动生成快
4. 适合中小型智能服务快速落地

不足：

1. 大规模复杂网关能力不如专门 API 网关
2. 中间件治理需要自己设计

### 为什么用 LangGraph

优点：

1. 适合多节点、可回退、带状态的工作流
2. 比纯函数串联更容易表达条件分支
3. 对 Agent 编排、RAG 编排很友好

不足：

1. 学习和调试成本高于简单函数流水线
2. 节点过多时可视化和排障复杂度会上升

### 为什么用 DashScope + text-embedding-v4

优点：

1. 中文语义能力较好
2. 与项目所在环境兼容性高
3. embedding 和生成模型来自同一生态，接入成本低

不足：

1. 批量 embedding 时吞吐受限
2. 成本和重建时间需要考虑

### 为什么用 ChromaDB

优点：

1. 适合快速搭建本地/单机向量检索
2. 开发和调试成本低
3. 支持 metadata 存储和 where 过滤

不足：

1. 大规模场景下治理能力有限
2. 对 metadata 格式有约束，空列表会报错
3. 数据迁移和版本管理要自己做好规范

### 为什么不是纯 LLM

原因：

1. 八字排盘、格局判断等底层能力需要确定性
2. 纯 LLM 容易幻觉
3. 规则引擎更容易解释、验证和回归测试

## 全方位技术深挖题库

[返回顶部](#top)

### 一、架构设计合理性与扩展性

#### 1. 为什么要把系统拆成多层，而不是单体逻辑直写？

考点：

1. 边界意识
2. 可维护性
3. 后续扩展性

回答要点：

1. 不同层职责不同
2. 便于替换某一层实现
3. 降低耦合，提升测试性

#### 2. API 层为什么不直接调用 RAG，而是走 Graph/Agent 层？

考点：

1. 编排层价值
2. 工作流状态管理
3. 业务流程扩展

#### 3. 如果未来增加塔罗、紫微斗数，当前架构能不能支撑？

考点：

1. 多 Agent 扩展
2. 多知识域扩展
3. 共享基础设施复用

### 二、技术选型原因和优劣分析

#### 4. 为什么用 LangGraph，而不是 Celery、普通函数编排或 Airflow？

考点：

1. 工作流粒度
2. 状态流转
3. 同步/交互式业务的适配性

#### 5. 为什么规则引擎和 LLM 要混合，而不是完全交给模型？

考点：

1. 可解释性
2. 稳定性
3. 幻觉风险

#### 6. 为什么用 metadata + where 过滤，而不是只做向量召回？

考点：

1. 精准过滤
2. 可解释性
3. 召回质量控制

### 三、性能优化策略

#### 7. 这个系统最主要的性能瓶颈在哪里？

候选瓶颈：

1. 文档预处理和切分
2. embedding 批处理
3. LLM 生成
4. 向量检索

#### 8. 你做过哪些优化？

你可以讲：

1. `.doc -> .docx` 缓存转换
2. 大文本切分优化
3. metadata 提取减负
4. Chroma 5000 条分批写入
5. `where` 过滤缩小候选集
6. Redis 缓存分析结果

#### 9. 如果用户量上来，哪几个环节最先扩容？

回答点：

1. LLM 推理成本
2. embedding 离线重建
3. API 层水平扩展
4. Redis / 向量库的外部化

### 四、安全性考虑

#### 10. 这个项目为什么需要安全模块？

原因：

1. 命理咨询场景容易碰到心理脆弱问题
2. 容易出现宿命论、迷信、极端建议
3. LLM 输出存在风险

#### 11. 你的安全策略是前置还是后置？

最佳回答：

1. 前置做输入检测
2. 后置做输出检测
3. 工作流里还要有兜底安全节点

### 五、可维护性与可扩展性

#### 12. 如何避免共享单例把系统弄得很难测试？

可以讲：

1. 无状态对象做共享单例
2. 有状态上下文做请求级工厂
3. `SessionContext` 替代全局状态管理器

#### 13. RAG 版本隔离为什么重要？

回答点：

1. embedding 模型变了，向量空间就变了
2. splitter 变了，chunk 分布就变了
3. 新旧索引混用会直接导致错误或召回污染

### 六、异常处理与容错机制

#### 14. Redis 挂了怎么办？

回答点：

1. 会话和缓存能力降级
2. 限流退到内存模式
3. readiness 可以降级为 degraded 而不是直接 not ready

#### 15. RAG 检索失败怎么办？

回答点：

1. 记录错误
2. 不让整个链路中断
3. 继续走基础分析和 LLM 生成

#### 16. 文档构建失败怎么办？

回答点：

1. 单文件超时控制
2. `.doc` 转缓存 `.docx`
3. 日志记录 + 跳过坏文件
4. 版本化 collection，避免污染旧库

## 标准回答示例

[返回顶部](#top)

### Q1：你为什么要用 LangGraph？

**标准回答**

> 因为这个项目不是简单的一次模型调用，而是一条带状态、带分支、带异常兜底的分析链。用户输入进入系统后，要依次经过输入验证、排盘、五行分析、格局判断、喜用神、流年、RAG 检索、LLM 生成和安全检查。  
>  
> 如果用普通函数串联，前期可以跑，但随着节点增多，条件跳转、失败回退和状态追踪会变得很难维护。LangGraph 的优势在于它天然适合这类“多节点 + 条件边 + 状态流转”的系统。我在这个项目里把每个分析步骤都做成独立节点，并通过路由函数控制后继节点，这样后续不管是扩新节点、做观测、还是做局部降级，成本都更低。

### Q2：为什么不是全 LLM？

**标准回答**

> 八字项目里有一部分能力必须保持确定性，比如四柱计算、五行分值、格局规则和喜用神判断的基础逻辑。这类内容如果完全交给 LLM，会有两个问题：第一是可解释性差，第二是结果不稳定。  
>  
> 所以我的设计思路是把系统拆成“规则层 + 知识层 + 生成层”。规则层负责确定性计算，RAG 负责补充知识依据，LLM 负责把结构化结果组织成更自然、更可读的分析文本。这样既能保留传统命理规则的稳定性，又能发挥大模型在语言表达上的优势。

### Q3：你们为什么要做 metadata 过滤？

**标准回答**

> 只做向量召回的问题是，语义相近不代表领域条件匹配。比如用户问“甲木七杀格怎么成格”，如果只靠 embedding，相似文本里可能混入很多“甲木”“七杀”“格局”分别相关但并不真正同时满足条件的 chunk。  
>  
> 所以我在 chunk 级别额外抽取了 `tiangan`、`dizhi`、`wuxing`、`shensha`、`geju`、`topic`、`sub_topic` 等 metadata。查询时先从 query 抽元数据，再构造 `where` 条件过滤候选集，然后才做向量检索。这样可以把召回范围先缩小到结构上更匹配的子集，提高准确率和可解释性。

### Q4：为什么做 Agentic RAG，而不是直接上 GraphRAG？

**标准回答**

> 我把这两者看成解决不同问题的方案。这个项目的核心难点，不是已经有一张高质量知识图谱等着查，而是用户问题形态复杂、命理知识半结构化、术语同义多、查询经常需要动态调整策略。  
>  
> 所以我优先做 Agentic RAG：先分析查询意图和复杂度，再决定检索策略、过滤条件、是否重写 query、以及结果是否需要继续补检索。  
>  
> GraphRAG 更适合实体关系已经非常稳定、图谱质量足够高、而且多跳关系推理是核心需求的场景。命理古籍文本目前还没有形成一张足够可靠的图谱，所以现阶段用 Agentic RAG 更贴合项目成熟度。未来如果图谱建设成熟，我更倾向于把 graph retrieval 作为 Agentic RAG 的一个工具接进去，而不是替代现有主链路。

### Q5：你做过哪些真正有技术含量的优化？

**标准回答**

> 我做过几类比较实用的优化。  
>  
> 第一类是构建链路优化。知识库里有很多 `.doc` 文件，直接用 Word COM 批量读取时会很慢也不稳定。我把它改成“.doc 先转缓存 `.docx`，后续直接复用缓存”的方案，显著降低了重建成本。  
>  
> 第二类是切分和 metadata 优化。我修掉了字符级切分尾部的循环边界问题，也把超大文本改成更线性的切分模式，避免在大文档上陷入深递归。同时把 metadata 提取收敛到真正参与过滤的字段，降低了构建期 CPU 压力。  
>  
> 第三类是检索和写库优化。写 Chroma 时我明确做了 5000 条分批写入，并且在写入前清洗 metadata，避免空列表导致 Chroma 拒绝写入。  
>  
> 第四类是运行时优化。我把 API 请求路径区分成普通路径和 LLM 路径，分别设置限流和超时策略，并且在 Redis 不可用时支持降级。

### Q6：如果 Redis 挂了，你的系统会怎样？

**标准回答**

> Redis 在这个系统里不是单点致命依赖。它主要承担缓存和部分会话加速能力。  
>  
> 如果 Redis 不可用，我做了三层处理：  
> 1. 依赖初始化层面允许单组件失败，不会因为 Redis 初始化失败把整个服务拖挂。  
> 2. 限流层会从 Redis 计数降级到进程内内存计数。  
> 3. 会话和部分缓存能力会退回到文件存储或无缓存模式。  
>  
> 同时 `/ready` 不会直接判整个系统不可用，而是将 Redis 标成 degraded。也就是说，系统仍然可以对外提供核心分析功能，只是性能和部分缓存能力会下降。

### Q7：你怎么解释“可维护性”？

**标准回答**

> 我理解的可维护性，不是代码写得工整就够了，而是当需求变了、依赖挂了、知识库版本变了、业务链路扩展了，系统还能低成本改动。  
>  
> 这个项目里我主要从三个方面保证可维护性：  
> 1. 结构上分层，把 API、工作流、RAG、基础设施拆开。  
> 2. 状态上把全局状态替换成请求级 `SessionContext`，降低并发和测试难度。  
> 3. 数据上对 RAG collection 做版本隔离，避免 embedding 模型或 splitter 变化时污染旧索引。

## 场景化面试题

[返回顶部](#top)

### 场景题 1：用户反馈系统今天一直超时，你怎么排查？

**答题模板**

1. 先看是全链路超时还是某个接口超时。
2. 再区分是 API 层、中间件层、Graph 节点还是外部依赖超时。
3. 检查日志和 trace_id，定位卡在哪个阶段。
4. 如果是 LLM 慢，先确认有没有走到 LLM 超时策略。
5. 如果是 RAG 慢，看是不是向量库或文档构建问题。
6. 最后给出短期止血和长期优化方案。

**你可以这样答**

> 我会先通过 access log 和 trace_id 判断超时集中在哪个接口，比如是 `/api/v1/bazi/analyze` 还是健康检查。  
> 接着我会看这个请求有没有进入 LangGraph，如果进入了，再判断是卡在规则计算、RAG 检索还是 LLM 生成。  
> 这个项目里我专门把 LLM 路径做了更长的超时配置，所以如果 `/api/v1/bazi/analyze` 被错误识别成普通路径，就可能 30 秒直接被切掉，这就是我会优先排查的一个点。  
> 如果定位到 RAG 层，我会进一步看 metadata 过滤条件、向量检索耗时、collection 是否匹配当前版本。  
> 短期止血可以先放宽 LLM 超时或降级跳过 RAG，长期会考虑异步化大模型调用、缓存高频查询和细化慢查询监控。

### 场景题 2：为什么知识库重建这么慢，你会怎么优化？

**答题模板**

1. 拆分阶段：文件读取 -> 清洗切分 -> embedding -> 去重 -> 写库
2. 找到瓶颈
3. 针对性优化

**标准回答**

> 我会把知识库重建拆成五个阶段：文档读取、文本清洗和切分、embedding、相似度去重、写入向量库。  
>  
> 实际排查中我就遇到过几个问题：  
> 1. `.doc` 读取通过 Word COM 批量处理太慢，于是我改成先转缓存 `.docx`。  
> 2. 超大文本切分在字符级 fallback 时存在边界 bug，导致尾部循环，我修掉了这个问题。  
> 3. metadata 提取做了过多衍生字段，导致构建期 CPU 负担很重，所以我收敛到真正参与过滤的字段。  
> 4. Chroma 不接受空列表 metadata，所以写入前必须做清洗。  
>  
> 优化策略上，我会优先做缓存、减少不必要 metadata、适度提高 embedding batch size、并行化非模型阶段、以及把去重和写库做成可恢复的流水线。

### 场景题 3：如果产品要求以后支持塔罗和紫微斗数，怎么扩？

**标准回答**

> 我会把扩展拆成三块：  
> 1. API 层新增路由或统一入口参数。  
> 2. Agent 层新增对应 Agent 和工作流图。  
> 3. RAG 层新增独立知识库、独立 collection 和独立 metadata schema。  
>  
> 关键不是复制代码，而是保证不同领域在 Agent 和 RAG 上隔离，而基础设施层保持复用。  
> 对外可以是一个统一平台，对内是多 Agent、多知识域、多工作流并存的结构。

### 场景题 4：如果 ChromaDB 里的索引版本和代码版本不一致怎么办？

**标准回答**

> 这是 RAG 系统里很典型的问题。我会先避免它发生，再考虑发现后怎么恢复。  
>  
> 预防上，我已经把 collection 名和 embedding 模型、splitter 版本绑定在一起，避免新旧索引混用。  
> 发现后，我会优先做版本检查，如果当前 collection 不存在或者维度不匹配，就直接报出明确错误或触发重建，而不是继续用错误索引查询。  
>  
> 对外服务上，为了不把整个业务链路打死，我也会保留 RAG 失败降级能力，让规则分析和 LLM 基础生成仍然可以工作。

### 场景题 5：如果面试官要求你把这个系统改成高并发在线服务，你会改什么？

**标准回答**

> 我会优先改三层：  
> 1. 运行时层：把 Redis、向量库、日志和配置都外部化，服务做无状态化。  
> 2. 模型层：把 LLM 和 embedding 调用做成更可控的异步/队列模式，并引入缓存。  
> 3. 检索层：把本地 Chroma 迁移到更适合多实例共享的向量数据库或托管检索服务。  
>  
> 同时会补充指标体系，比如 P95 延迟、命中率、限流触发率、RAG 检索成功率、LLM 错误率和降级率。  
> 我会优先保证“服务可用 + 结果质量可控”，而不是一上来追求极限并发。
